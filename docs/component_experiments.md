# 业务组件定向实验结果

政策时效过滤改善了有效版本的首位命中，真实模型业务结果持平。确认偏好召回减少了用户补充
和模型请求，严格文本完成数为 10/12，空结果对照为 12/12。提交后丢失响应时，只读对账
保持单次业务提交，并增加了读取请求。

真实模型使用配置名 `gpt-6-luna`，业务后端和场景数据为合成夹具。政策组包含八次执行；
Memory 正式组包含六个场景、两种条件、两次重复，共 24 次执行。重复执行与独立场景分别计量。
原始评分、逐请求用量、业务终态、源码指纹和校准记录均保留。

## 政策时效

使用 24 份合成政策和 12 条查询，比较仅按业务范围检索与同时按有效期筛选。
其中九条查询有适用依据，两条查询没有适用文档，一条查询与现有政策无关。
两组的 BM25、业务范围、全文读取、工具定义与 Agent 权限一致。

| 指标 | 仅范围过滤 | 范围与有效期过滤 |
| --- | ---: | ---: |
| 九条可回答查询的有效版本 Hit@1 | 1/9 | 9/9 |
| 九条可回答查询的有效版本 Hit@3 | 9/9 | 9/9 |
| 返回文档中的时效不适用项 | 21/30 | 0/18 |
| 无适用文档时正确返回空结果 | 1/2 | 2/2 |
| 真实模型任务完成数 | 4/4 | 4/4 |
| Agent 模型请求 | 47 | 45 |
| Agent 逻辑输入 Token | 251,170 | 239,702 |

真实模型部分包含两个场景、两个条件、两次重复，共八次执行，使用合成 Redmine HTTP 服务。
四次跨会话恢复均在准备阶段读取 v1、在政策生效时间切换后读取 v2；所有执行都产生一条
有回执的当前政策备注并保留工单状态。模型请求共 92 次，用量记录完整。

这个开发集呈现检索排序改善与业务任务完成数持平。两组均保留可读取的当前版本和历史版本；
已有历史信息与新读取结果共同参与模型决策。

## 确认偏好召回

建立阶段通过生产确认 API 将相同偏好存入 SqliteStore，随后关闭 Store，在同一工单范围的新
thread 中继续任务。两组共享模型、工具定义、Skills、政策、权限和任务输入，仅改变偏好查询
返回值。空结果组可询问缺少的偏好，固定用户脚本提供补充，后续调用全部计入。
补充答复包含已经组装的完整目标备注；可召回组依据格式规则与当前事实自行组装。
因此，完成数采用固定用户补充策略下的精确匹配口径，同时呈现这两条处理路径。

| 指标 | 可召回确认偏好 | 返回空结果 |
| --- | ---: | ---: |
| 严格文本任务完成数 | 10/12 | 12/12 |
| 需要历史偏好的子集完成数 | 6/8 | 8/8 |
| 当前指令覆盖旧偏好子集完成数 | 4/4 | 4/4 |
| 历史偏好补充次数 | 0 | 8 |
| 全部用户补充次数 | 0 | 9 |
| Agent 模型请求 | 83 | 138 |
| Agent 逻辑输入 Token | 351,703 | 651,680 |
| Agent 输出 Token | 3,576 | 6,398 |
| Agent 缓存输入 Token | 260,736 | 499,712 |
| 基础设施异常 / 用量未知请求 | 0 / 0 | 0 / 0 |

十二对执行中十对完成结果持平，两对空结果组完成而可召回组失败。两次失败均发生在
`log_summary`：模型召回了正确字段格式，写入时省略了原文句点，未达到冻结的文本精确匹配要求。
回执、单条备注和其余工单字段检查均通过，失败正文与评分完整保留。

该结果呈现“较少补充与调用”和“严格格式完成数下降”的共同表现。输入 Token 包含缓存输入，
全量分母包含两次失败；模型费用保持未定价。这里统计的是固定用户脚本提供偏好的次数。

三轮四次执行的校准组共 112 次模型请求，正式组为 221 次，分别保存。校准记录包含可评分业务
失败、查询分支检查和参数说明调整；正式 24 次使用同一冻结协议。政策与 Memory 正式组共
313 次模型请求，连同 Memory 校准共 425 次，连接探测独立计量。

## 响应丢失与对账

合成服务固定 100 对独立备注操作，每种策略包含 50 个正常操作与 50 个“提交成功后响应丢失”
操作。对照为持久化发送状态、至多重发一次的 at-least-once 策略；生产方案使用
`RedmineClient`、`SqliteStore` 与只读回执对账。

| 指标 | 普通重试 | 生产对账 |
| --- | ---: | ---: |
| 业务完成 | 100/100 | 100/100 |
| 重复备注 | 50 | 0 |
| HTTP 写入与服务端提交 | 150 | 100 |
| 总 HTTP 请求 | 450 | 600 |
| 最终结果未知 | 0 | 0 |

两组正常操作均保持一条备注；响应丢失子集中，生产对账保持单次提交，并恢复可核验回执。
其代价包括更多的业务读取。故障比例按首次操作计，重发响应正常送达。

迟到提交、提交后 Checkpoint 间隙各执行两种策略，生产方案均从新 Python 进程继续原生会话，
保持一次提交。撤权另设一个固定调度、四个子进程，撤权成功后四次 HTTP 请求全部为读取。
这些确定性案例描述所覆盖的调度，墙钟恢复耗时与广泛并发可靠性使用独立测量。

## 既有冻结基准

CRM-Agent-Bench 的十二题留出继续保持原始任务及评分。基础方案与组件增强方案均为 11/12，
逐题全部持平；基础方案 Agent 逻辑输入为 214,692，增强方案为 262,371，前者少 18.2%。
这一口径包含全部十二题及失败题，逻辑输入包含缓存输入。

政策、Memory 和故障场景分别使用独立的任务清单与评分，数据集身份、重复、模型及合成服务
口径各自保留。[冻结基准结果](results.md)。
